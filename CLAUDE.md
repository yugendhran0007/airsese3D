# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm start` — **the command to run the app locally.** Builds and serves the production bundle on port 4173 with `--host` (so a TV or phone on the same network can open it). Use this, not `npm run dev`, whenever the point is to *look at* the office rather than edit it: measured on the target machine, the dev server burns **8.17 s of main-thread script time per 20 s** against the production build's **4.70 s**, and 70 MB of JS heap against 39 MB. That is React's dev build plus Vite's on-the-fly transforms, and it is spent on exactly the main thread the frame loop needs.
- `npm run dev` — Vite dev server (default port 5173; picks the next free port if taken). For editing, not for judging performance.
- `npm run build` — `tsc --noEmit && vite build`; the build is typecheck-gated and fails on any type error
- `npm run typecheck` — `tsc --noEmit`
- `npm run preview` — serve the production build

There is no lint script, no ESLint config, and no test runner — verification is typecheck + driving the app. Package manager is npm (`package-lock.json`). `vite.config.ts` is minimal (react + tailwind plugins, raised `chunkSizeWarningLimit`); there is no `.env` and no path aliases.

**Headless verification** (no GPU needed): `node scripts/verify.mjs <url> <shot.png> [waitMs]` launches system Chrome via puppeteer-core, screenshots the app, and dumps live engine state through the dev-only globals `window.__engine`, `window.__ui`, `window.__char`, `window.__scenario`, `window.__scene` (the three.js scene graph). `node scripts/shot.mjs <out.png> '<json>'` screenshots a given view: `{"cam":[x,y,z]}` (orbit camera position), `{"mode":"follow","tele":[x,z,heading]}` (teleport the player, chase cam), `{"render":"stylized"}` — it hardcodes `localhost:5173/?nofx` and also needs `window.__camera`. Other `scripts/*.mjs` (`diag`, `closeup`, `interact*`, `finalshots`) follow the same pattern but hardcode `localhost:5183` (also `verify.mjs`'s default when no URL is given) — edit the port to match your dev server. `scripts/_*_tmp.mjs` are throw-away experiments, not tooling. All scripts launch `/usr/bin/google-chrome` with SwiftShader. Append `?nofx` to the URL when running under SwiftShader for usable FPS; realistic mode needs ~60–90 s to mount headlessly, so wait on `window.__scene` rather than a fixed delay. The dev globals are installed from `simStore.ts` (`__engine`, `__ui`), `characterStore.ts` (`__char`), `scenarioPlayer.ts` (`__scenario`) and `Scene.tsx` (`__scene`, `__camera`, `__gl` — the WebGLRenderer, handy for `__gl.info.programs`). Measure load smoothness against a **production build** (`npm run build` + `npm run preview`), never the dev server: dev's on-the-fly transforms and React dev mode roughly double both the load time and the hitch count, and the `__scene`/`__ui`/`__engine` globals do not exist in a production bundle, so a driver must take readiness from the DOM (the loading screen unmounting) instead. Frame-rate numbers on an integrated GPU swing ±40 % run to run — the same build at the same canvas size measured 26–45 fps across runs — so **fps cannot settle a small optimisation here**. Prefer deterministic counters as evidence: `__gl.info.render.calls` after an explicit `gl.render(...)` (reading it without forcing a render returns a partial frame), visible mesh counts, and canvas megapixels. Note also that `PerformanceMonitor` moves the canvas size between runs, so always report fps *with* its megapixel count or the comparison is meaningless. Reference point for the presentation target (production build, realistic + TV mode + auto-tune, 2560x1440 viewport, Intel UHD): auto-tune settles on the bottom rung, canvas 1484x835 / 1.24 MPix, at ~32-47 fps. It sits on the bottom rung because climbing one costs 1.46x the pixels — this machine has to get ~1.4x faster before surplus can be spent on sharpness instead of frame rate. For load-time profiling use a **headed** Chrome on the real GPU (`headless: false`, `DISPLAY=:0`, `--ignore-gpu-blocklist`): SwiftShader inflates shader-compile and texture-upload costs ~10× and headless Chrome cannot reach the AMD GPU here. Chrome's on-disk shader cache makes repeat loads much faster than a fresh puppeteer profile shows — measure both. **On the dev laptop (ASUS TUF F15, Optimus), check which GPU Chrome is actually on before measuring anything**: Armoury Crate's *Eco* GPU mode turns the RTX 3050 off entirely (`HKLM\SOFTWARE\ASUS\Armoury Crate Service\GPUMode` → `IsEcoMode` = 1; `Get-PnpDevice -Class Display` lists the 3050 as `CM_PROB_PHANTOM`) and everything then renders on the Intel UHD with 128 MB of VRAM at ~20 fps, which no code change recovers — the fix is Armoury Crate → GPU mode → Standard/Ultimate, then Windows Settings → Display → Graphics → Chrome → High performance. The WebGL renderer string (`WEBGL_debug_renderer_info`) is the ground truth for which chip drew the frame. On Windows the scripts' Chrome path is `C:/Program Files/Google/Chrome/Application/chrome.exe`, and headless Chrome there reaches the real GPU (ANGLE D3D11), so no SwiftShader flags are needed.

`node scripts/optimize-avatars.mjs` regenerates the human GLBs in `public/models/people/` from the untouched originals in `models-original/` (not served): strips the VALID avatars' 96 facial morph targets, downsizes textures to 1024² WebP and re-meshopts them (1.8 MB → 0.65 MB each), and reduces `Soldier.glb` to bone nodes + clips (2.1 MB → 0.4 MB). `OUT_DIR=public/models/people-lite MAX_TEX=512 SIMPLIFY=0.4 node scripts/optimize-avatars.mjs` builds the **lite tier** (512² textures, 40 % triangles, ~0.33 MB each) used by Fast/Balanced; `tierUrl()` in `realisticPeople.ts` picks the folder from `uiStore.quality` (the player avatar always uses the full asset). Re-run both after replacing any source model.

## What this app is

AirSense (`md` at the repo root is the full 65-section spec; `itmd` is a condensed restatement; README.md has the feature tour): a frontend-only, real-time 3D visualization of indoor air quality in a Chennai IT office. Live outdoor weather/AQI from the **keyless** Open-Meteo APIs feeds context into a browser-side physics simulation (CO₂/temperature/humidity per zone), rendered as a walkable React Three Fiber office. There is no backend, no API keys, no `.env`.

## Architecture

### The signature pattern: per-frame data never enters React

- `src/simulation/engine.ts` exports a singleton `engine` (class `SimulationEngine`, plain TS, no framework). It ticks on a 10 Hz `setInterval`, integrating physics in Euler substeps at 60 sim-seconds per real second × speed.
- R3F components read `engine.snapshot` / `engine.params` **directly inside `useFrame`** at 60 fps with zero re-renders.
- The DOM gets throttled 4 Hz snapshots via zustand (`connectEngine()` in `src/state/simStore.ts` wires engine listeners into the store).
- The player character's per-frame position lives in the mutable `characterTransient` object (`src/state/characterStore.ts`), not React state; the store itself only holds coarse zone crossings.
- The scenario player (`src/simulation/scenarioPlayer.ts`) and ramp mode (`src/simulation/rampMode.ts`) are module-level state stepped from `useFrame`.

When adding features, follow this split — do not lift per-frame data into zustand.

### Data flow

```
OutdoorProvider (Open-Meteo | Dummy | Sensor-stub)
  → weatherPoller → weatherStore → engine.setOutdoor()
engine (10 Hz physics, 4 zones + inter-zone mixing, ring-buffer history)
  → 4 Hz snapshots → simStore → DOM panels/charts (Recharts)
  → read directly in useFrame → 3D scene
```

- **Engine is the source of truth for `params`**: every `simStore` mutator writes to the engine first, then mirrors `engine.params` back into the store.
- Four zustand v5 stores: `simStore` (params/thresholds/snapshot/alerts), `uiStore` (mode, cameraMode, `renderMode: 'realistic'|'stylized'`, panel flags, selections), `weatherStore` (outdoor reading + staleness), `characterStore` (zone only).
- Physics lives in pure functions in `src/simulation/physics.ts` (all rates per-hour); zones are a 2×2 grid defined in `src/simulation/zones.ts`; status/alerts/recommendations in `statusEngine.ts` / `alerts.ts` (60 sim-second hysteresis to prevent flapping) / `recommendations.ts`.
- The provider seam (`src/providers/OutdoorProvider.ts`) is sacred: future real sensors (ESP32, spec §39–42) must arrive as one new provider implementation with zero frontend changes. Weather polling handles backoff, keeps the last reading, and marks it STALE after 20 min — never silently passes stale data off as live.

### 3D scene

- `src/scene/Scene.tsx` is the `<Canvas>`; `OfficeWorld` inside it is the branch point for the **Realistic / Stylized render-mode toggle** (`uiStore.renderMode`, default realistic, "Real/Styled" button in `TopBar`).
- Realistic mode is modelled on a modern IT-office fit-out (white bench desks with grey privacy screens and beige pedestals, black mesh task chairs, grey carpet, suspended tile ceiling with linear LED bars/downlights/pendants, 4-way AC cassettes, fire-exit signs, white columns). It is almost entirely procedural: `RealisticFurniture.tsx` (desks, chairs, meeting tables, `Cafeteria` with round tables/teal lounge chairs/coffee counter, white lockers) and `RealisticCeiling.tsx` build instanced parts via the generic `Instanced`/`Part` helper. The only GLTFs left are KayKit planters/books (`GltfInstances`) and the humans.
- **Do not try to merge a VALID avatar's submeshes.** Each avatar is split into ~5 skinned meshes (body, `h_L_eye`, `h_L_gland`, `h_R_eye`, `h_TeethDown`) that share material, bones, node transform and bindMatrix — but each carries its **own `boneInverses`** (a different bind space) and meshopt-quantized `Int16` positions, so `mergeGeometries` + a single `bind()` shreds them into stretched shards. This was tried and reverted; the ~268 skinned draws for ~56 characters are the cost of these assets.
- Seated-avatar performance rules (`RealisticCrowd.tsx`): skinned meshes are **frustum-culled** using `SkinnedMesh.computeBoundingSphere()` taken after posing (padded ×1.25) — do not set `frustumCulled = false` on the seated crowd again; they **cast no shadows** outside ultra (the shadow pass would re-skin them); beyond `ANIM_LOD_DIST` (22 m) their micro-animation is skipped; beyond `FACE_LOD_DIST` (7 m) the six facial submeshes (eyes, glands, teeth) are hidden, which is where most of the draw-call win lives. **That LOD now lives in `realisticPeople.ts` (`collectFaceParts` / `faceLodDistance` / `applyFaceLod`) and every skinned character uses it** — the seated crowd, the walkers, the player and the presenter. It is a property of the avatar asset, not of the crowd: while it was implemented only inside `RealisticCrowd`, everyone else drew full faces at any range, which measured as 105 sub-pixel facial draws with the camera 22–51 m away. Wiring the shared helper into the other three took visible skinned meshes from 154 to 76. Any new avatar-backed component must call it too — each avatar is ~7 skinned draws and six of them are these sub-pixel face parts, so at 37 avatars this drops ~150 of 268 skinned draws. They share the body's `_Body` material, so popping them back in compiles nothing. **Gate that LOD on the meshes' real `visible` flag, never a remembered one**: `useAsyncCompile` reveals a subtree by setting `visible = true` on every mesh it hid at mount, so a cached boolean desyncs the first time an avatar streams in and the LOD then never re-applies. Desk/meeting sitters look down at their laptop (`applyPose`) and type via alternating `WorldXRotator` forearm taps with pauses.
- Humans: VALID-library business avatars (`public/models/people/*.glb`, CC-BY 4.0, meshopt-compressed) for the seated crowd (`RealisticCrowd`, first `REALISTIC_PER_ZONE` = 24 per zone (`RealisticCrowd.tsx`); `Crowd` fills overflow with `skipFirst`), the player (`RealisticBody`) and six walkers (`WanderingNpcs`). Animation comes from the three.js Soldier GLB's Mixamo clips via `retargetMixamoClips` in `realisticPeople.ts` — a **world-space** retarget (sample the clip on a Soldier clone, apply each bone's world-rotation delta from its T-pose to the VALID bone's T-pose, convert back to local). Do not go back to copying local quaternion tracks: the two rigs' bind poses differ (Soldier's Hips sits under a −90° X node; VALID bakes axis conversion into bone rests) and that lays avatars flat. Likewise static poses use `rotateBoneWorld`/`WorldXRotator` (world axes), never `bone.rotateX`. VALID rigs carry their cm→m scale on the Hips bone, so scale tracks are dropped; avatar height is measured from the Head bone, never `Box3.setFromObject`. Rest-relative retargeting keeps the rig's own +Z facing, so there are no `rotation-y={Math.PI}` wrappers on VALID avatars.
- Walkers are **frustum-culled** like the seated crowd (padded bind-pose bounding spheres, ×1.6 since an animated pose overflows the bind pose): six walkers at ~7 skinned draws each is 42 draws that were being submitted even with every one of them behind the camera, which walking the office in full mode is most of the time. Measured from an in-office camera the whole scene is 216–224 draws against 360 from the overview.
- Walkers follow waypoint routes in `WanderingNpcs.tsx` with Idle pauses (`pause`/`face`): side corridors at x = ±(W/2 − 1.6), the z = 0.5 cross aisle, the x = 0 spine, room doors, and the cafeteria walkway. Routes are hand-built from `layout.areas`; if you change the layout, re-check them against `layout.obstacles` (a throw-away script that samples each segment against the obstacle circles is the quickest way).
- Every GLTF component sits in `<Suspense>` with its procedural equivalent as fallback (`RealisticFurniture` → `Furniture`, `CustomOffice` → `OfficeShell`), so missing assets degrade instead of breaking.
- Light rig by tier (`Lighting.tsx`): Fast = ambient + hemisphere + key (no shadows); Balanced adds the cool fill and shadows; only 8K/ultra has the four point lights (per-fragment cost on every material) — the PMREM environment carries the ceiling glow instead. **In realistic mode the flat terms are deliberately small** (ambient 0.45, hemisphere 0.45) and `environmentIntensity` is 1.15 outside ultra: the environment map *is* the room's ambient light, and unlike a constant term it has direction — bright from the window wall and the LED grid, dim under the desks. Stacking a large `ambientLight` on top added the same energy again with no direction, which lit every surface identically regardless of where it faced and made the office read as evenly washed plastic. Do not raise the flat ambient to "brighten" realistic mode; raise `environmentIntensity` or the key light, or the contrast the HDR rig exists to produce is cancelled out. Tone mapping is **AgX** at exposure 1.45 (`Scene.tsx`); `index.html` preloads the first GLBs.
- Realistic-mode lighting is image-based: `RealisticEnvironment.tsx` builds its own HDR office light rig (mullioned daylight window wall, rows of individual LED tubes, warm side spots, theme-tinted feature wall, brighter floor aisle) and bakes it through PMREM into `scene.environment` — no HDR asset to load. **Resolution is tiered** via `fromScene(..., { size })`: 128² Fast, 256² Balanced, **1024² ultra**, with a smaller blur sigma at ultra so window/LED shapes survive; the cube camera sits at eye height (y=1.6). The rig is modelled with real gaps (mullions, dark runs between tubes) — a flat emissive panel bakes to a featureless smear at any resolution. Emissive values ≫1 there are intentional.
- **Room & HVAC card** (`src/ui/dashboard/HvacCard.tsx`, card id `hvac`): room dimensions and volume next to the air actually being moved through them — air changes/hour, outdoor air in L/s, **L/s per person** banded green/amber/red (≥10 good, ≥5 marginal, below under-ventilated), the mechanical-vs-natural split, and the steady-state CO₂ the current occupancy and ventilation settle at. It derives everything from the same `achFresh()` the engine integrates with, so the readout cannot drift from the simulation it describes. This is the card that makes invariant 3 visible instead of asserted: occupancy alone is not danger, it is generation against air changes, and putting the two numbers side by side lets the sliders prove it. It reads `simStore.params` — safe because every mutator (including the scenario player and ramp mode) writes through the store, which mirrors the engine; calling `engine.setParams` directly would leave this card stale.
- **Air-aware seating** (`seatPicking.ts`): `bestAirSeat()` scores free seats by their zone's CO₂ above baseline plus a status penalty, with distance at a deliberately gentle 12 ppm/m — crossing the office for genuinely cleaner air is worth it, walking to the far corner to save 20 ppm is not. **F picks by air, not proximity**: CO₂ builds where people are, so the nearest free chair is often in the air you just left. Verified: standing in a red zone at 1562 ppm, F walked the avatar across the office to the cleanest zone at 993 ppm. `SeatTargets` tints each free-seat marker by `seatStatus()` on the same `STATUS_COLORS` scale as the occupants' safety rings, eased per frame — choosing a chair is choosing air. The player's own ring in `PlayerCharacter` beats faster and harder as its zone worsens (2.6 → 7.5 rad/s): a colour is read once and then stops being noticed, a change of rhythm keeps signalling.
- **Employee mode** (`uiStore.employeeMode`, "Anon/Employees" button in `TopBar`): name tags are hidden by default and shown for everyone only in employee mode (a clicked person's tag always shows). Every occupant has a floor **safety ring** coloured by `personStatus(seed, zoneStatus)` in `effects.ts` (green safe / yellow medium / red danger); `RealisticCrowd` draws all rings in one `SafetyRings` instanced mesh, `Crowd` uses the same helper for its instanced ring. Keep rings + tag dots + inspector using that one function. The **player carries no label at all** — the "YOU" `Html` tag was removed at the user's request: you already know which body you are driving, and a DOM tag pinned over its head sits between the camera and the office. The pulsing status ring is the player's only marker.
- `WallTvs.tsx` plays **only** the Finstein brand animation (user's explicit choice — no slides, ticker or data): stepped-F mark builds, wordmark wipes, tagline fades, light sweep + breathe, clean 8 s loop, over a drifting-network background. Painted into a shared `CanvasTexture` from `useFrame`; the deck is authored in 1024×576 units and scaled via `ctx.setTransform` per quality tier.
- **Data Viz** (`src/ui/dataviz/DataVizOverlay.tsx`, `uiStore.dataVizOpen`, "Data Viz" navbar button): a people-unit view — one glyph (Human mode) or LED seat-cell (Digital mode) per occupant in the 2×2 zone grid, coloured by `personStatus` with a posture/icon + label, hero counts, threshold "breath meters" and a table view. It reads the 4 Hz store snapshot only. Per-seat readouts show the **zone** reading — there are no per-seat sensors, never invent per-person values.
- **Quality tiers** (`uiStore.quality`: `'fast' | 'balanced' | 'ultra'`, persisted in `localStorage` `airsense.quality`; Fast/Bal/8K segmented control in `TopBar`; `ultraQuality` is the derived boolean). **Fast** is the production-lightweight tier: DPR ≤1, no key-light shadows, no postprocessing, **no reduction in avatar count at all** — `REALISTIC_PER_ZONE` is `Infinity` at every tier, because every occupant being a real VALID human was the user's explicit choice over capsule overflow. Tiers differ only in asset weight (Fast/Balanced stream the lite 512²/40 %-tri GLBs via `tierUrl`), animation LOD and shadows. This matters for performance work: skinned avatar draws are the measured cost centre (~a third of the frame; hiding them took 47.8 → 71.4 fps), and **no quality tier touches them**, so switching to Fast does not relieve the one thing that is actually expensive, TV at 1024² @12 fps, screen textures @3 fps; `PerformanceMonitor.onFallback` auto-drops Balanced → Fast, and on first visit `recommendQuality()` (`src/utils/hardware.ts`: cores/RAM/GPU renderer string) picks the starting tier so integrated-GPU laptops begin in Fast. The Canvas sets `frameloop='never'` while the tab is hidden; `SceneErrorBoundary` (App.tsx) replaces a crashed canvas with a GPU/acceleration hint. **8K/ultra** pins canvas DPR at the device max (≤2), renders the TV deck at native 4K (3840×2160) and monitors at 2×, 4096² shadow maps, max anisotropy. The TV deck is authored in 1024×576 units and scaled via `ctx.setTransform`, so never hardcode pixel sizes in `WallTvs.tsx` painters.
- **Presentation / TV mode** (`uiStore.tvMode` + `tvBudgetMp`, persisted in `localStorage` `airsense.tvMode` / `airsense.tvBudgetMp`; "TV" button + resolution select in `TopBar`). For driving a large external display — the 64" 8K TV target. The Canvas `dpr` prop is a *multiplier* on the CSS viewport, which is the wrong control on a huge panel: an 8K TV resolves as either a 7680×4320 viewport at `devicePixelRatio` 1 or ~2560×1440 at 3, so the normal path asks for **33 MPix** or 15 MPix a frame (33 MPix reliably kills the renderer process on a 4 GB laptop GPU). TV mode instead derives the multiplier from an **absolute pixel budget** via `dprForBudget()` in `src/utils/renderScale.ts`, so one setting behaves identically on a laptop panel, a 1080p projector and an 8K television. The budget is a **ceiling, not a target**: `dprForBudget()` clamps to the device's own pixel ratio, because a viewport *smaller* than the budget would otherwise be supersampled — measured on an Intel UHD, a 1920×1080 viewport under the 3.7 MPix budget rendered 2.79 MPix at 24 fps, slower than the same scene on a 4K viewport where the budget actually bound (1.24 MPix, 36 fps). Rendering below native is not a downgrade here — a 64" 8K panel is ~138 PPI and the eye cannot resolve that at presentation distance, the TV's upscaler covers the gap, and because only the WebGL canvas is scaled the **DOM panels keep rendering at the display's native resolution**. TV mode also *pins* quality for the length of a talk: `PerformanceMonitor`'s DPR steps and its Balanced → Fast fallback are skipped, `Effects.tsx` never takes its sustained-slow-frames postprocessing bail-out (SMAA matters **more** when rendering below native, and once dropped it never came back), and `RealisticEnvironment` bakes the 1024² PMREM cube at any tier. Finally `App.tsx` scales the DOM shell by `uiScaleForWidth()` — panels are sized in CSS pixels, so on a 7680-wide viewport they keep laptop size and become unreadable from across a room. Do not "fix" TV mode by raising DPR toward native; the budget is the point.
- **Auto-tune** (`src/utils/autoTune.ts`, `uiStore.autoTune`, persisted in `localStorage` `airsense.autoTune`, default on; readout + switch live in the navbar Performance popover). A closed loop that measures the real frame rate and walks a nine-rung `DETAIL_LADDER` (`Maximum → High → Clear → Balanced → Smooth → Fluid → Lean → Light → Minimal`) until the picture holds ~60 fps, so a large display stays smooth without the user touching a setting. One `useFrame` drives it (`AutoTuner` in `Scene.tsx`); the controller keeps **module-level** state and publishes through `useSyncExternalStore` (`useDetailLevel()` for the DOM, `detailLevel()` for `useFrame`) — do not add a fifth zustand store for it. Each rung carries `renderScale` (a multiplier folded into the Canvas `dpr`, on top of whatever the tier or the TV budget asked for), `postFx`, `animDist` and `faceDist` (the seated-crowd LOD distances, which `RealisticCrowd` reads per person). **Ladder order encodes an explicit user priority — smoothness first, realism second, unnecessary effects last** — so each rung sheds whatever is least load-bearing for *understanding the office*: decorative effects first (bloom and vignette, then airflow-particle density), then post antialiasing (SMAA goes after the decoration, and costs less than it looks like because the canvas carries MSAA), then distant detail (facial submeshes, then micro-animation), and **render scale last and gently** — the top two rungs do not touch it, `Fluid` stops at 0.85, and only the three rungs below it (`Lean` 0.75 → `Light` 0.65 → `Minimal` 0.5) move *nothing but* render scale. Render scale is still the biggest single lever, which is why an earlier version of this ladder pulled it *first*; it was moved to the end because on a 64" panel resolution is the clarity of the infrastructure and the people, and the brief puts that above every effect. **Whether resolution buys anything depends on which GPU is drawing**: on the RTX 3050 it is free (0.44 / 0.73 / 1.15 MPix all ~30 fps — that chip is bound by skinned-avatar vertex and draw work), so it settles above those rungs; on the Intel UHD it is the only lever left (fixed camera, interleaved A/B: 1.50 MPix 14–18 fps, 0.52 MPix 22–25 fps), which is what the bottom three rungs are for. Below ~0.5 MPix the Intel gains nothing either (0.28 MPix ran at the same 22–25 fps), so `Scene.tsx` clamps the final canvas to an absolute `MIN_RENDER_MPIX` = 0.5 floor that binds only when the scale pushed it under — a ratchet cannot detect "no longer helping" by itself. The **settled rung is remembered** (`localStorage` `airsense.detail`) and the next load starts there instead of at `High`: walking the ladder costs two slow windows plus a settle per rung, ~20 s of stutter on a machine that belongs at the bottom, and it was paid on every visit. It only seeds the start — the ratchet still climbs if the machine got faster. `postFx` is therefore `'full' | 'aa' | 'none'`, not a boolean. **Shadow maps and skinned-avatar count are deliberately NOT on the ladder** — pulling either recompiles shaders and costs a multi-hundred-ms freeze, and a lever that costs a hitch to pull cannot be used to buy smoothness. A rung change re-enters R3F's `setDpr` → `setPixelRatio` → `setSize`, which reallocates the (MSAA) drawing buffer — instrumented at **two `setSize` calls per step**. That stall is far below `STALL_S`, so without help the controller measures its own resize and reads it as evidence to step again; `SETTLE_MS` (700 ms) discards frames after a change, which halved measured resize churn over a load (12 → 6 `setSize`) at the same settled rung and frame rate. **Do not make a down-step a revertible probe** — the idea that "if the rung below is no faster, hand the resolution back" fails because one rung is only ~16 % of the pixels, under the frame-time noise of a one-second window, so it stops after one step: A/B'd at **1.12 MPix / 18 fps / p95 174 ms** against the plain ratchet's **0.43 MPix / 71 fps / p95 42 ms**. Note also that the settled rung is **not deterministic** — identical builds settled at 0.43 and 0.65 MPix on consecutive runs — so never conclude a rung change from one run. It climbs slowly (6 good windows) and drops quickly (2 bad ones, or a *single* window under `VERY_SLOW_FPS` = 30 — at that frame rate the second window is a second of stutter spent confirming the first), stops stepping after `MAX_STEPS` so nothing shifts mid-presentation (`autoTuneLocked()` shows as "settled"), and `resetAutoTune()` runs on any quality / render-mode / TV-mode change. `STALL_S` = 2 s: a frame slower than that is treated as a stall (tab wake, GLB decode) and discarded, but the threshold must stay well above the frame times the controller exists to rescue — at 0.5 s it discarded *every* sample on a slow machine and went blind at exactly the moment it was needed. While auto-tune is on, `PerformanceMonitor`'s DPR steps and its Balanced → Fast fallback are skipped and `Effects.tsx` never takes its own slow-frame bail-out: two controllers fighting over the same number is how a picture ends up pulsing.
- **Alerts are a navbar notification** (`src/ui/alerts/NotificationBell.tsx`), not a floating stack. The old `AlertsPanel` toasts sat over the office — on a large display three alerts covered a whole meeting area — and it was also the panel that buried the navbar popovers. The bell shows a count badge coloured by the worst active severity, opens a popover listing every alert with its recommendation, and **shakes when the count rises** (never on the way down, never on first render), because a silently incrementing number is easy to miss. It is always in the bar, collapsed or not: a notification you must expand a menu to discover is not a notification. Related fix: the header now carries **`z-50`** — `.glass` sets `backdrop-filter`, which creates a stacking context, so a popover's own z-index competes only *inside* the header, and without a z-index there the whole bar paints in DOM order and loses to every dashboard panel declared after it.
- **Navbar control cluster** (`src/ui/controls/ControlCluster.tsx`): the simulation knobs are a row of symbols in `TopBar` (people, ventilation/HVAC, openings, room size, initial conditions, performance), each opening a popover; only one is open at a time. This replaced the fixed 16 rem left `ControlDrawer` (deleted) — a drawer costs the same *fraction* of a large screen while the office behind it is the point. Two constraints on the popovers: they are plain absolutely-positioned children of the header, **never portals**, because the shell is scaled by a CSS transform in TV mode and a portal to `document.body` escapes it; and the header is `flex-wrap`, **never** `overflow-x-auto`, because a scroll container clips popovers that hang below the bar. Escape is handled in the **capture** phase with `stopPropagation()` so it closes the popover without also dropping the camera out of follow mode. `PerfReadout` polls `measuredFrameRate()` on a 500 ms interval — never per frame.
- **Full mode** (`uiStore.fullMode`, "Full" button in `TopBar`, Esc exits): browser fullscreen plus a bare walkable office — every DOM panel gone, the navbar auto-hiding to a top-edge strip. `fullMode` is **not persisted**: `requestFullscreen` needs a user gesture, so a restored `true` would desync on the next load. It is kept separate from the actual Fullscreen API call for the same reason — fullscreen can be refused, and when it is, hiding the panels is still most of what was asked for; `App.tsx` listens for `fullscreenchange` because Esc/F11/window chrome can all leave fullscreen without going through the button. `useTopEdgeReveal` in `TopBar` derives reveal from one window `mousemove` plus a **hit-test** against the header ref (and a held pointer button, which covers dragging a slider off the panel) — not React `onMouseEnter`/`onMouseLeave`, whose leave event can be swallowed by the bar fading to `pointer-events-none` under a resting pointer, leaving it stuck visible. `Shortcuts` stays mounted (the keyboard is most of how you drive the bare office) but hides its floating help button.
- **Closing UI (🗙)**: every card/drawer/overlay closes with the 🗙 symbol (`CloseX` in `src/ui/shell/CloseX.tsx`). Dashboard cards are wrapped in `Closable` (hidden state in `uiStore.hiddenCards`); self-positioned panels (navbar, HUD, scenarios, mini-map) use `Closable bare` + their own inline `CloseX`. The `RestorePill` (bottom-right) re-opens closed cards. Keep new panels on this system and use the 🗙 glyph, not lucide `X`.

- `ShadowScheduler` (`Scene.tsx`) sets `gl.shadowMap.autoUpdate = false` and refreshes the map every 4th frame (2nd in ultra), plus continuously for an 8 s warm-up while GLTFs stream in and whenever room/quality/renderMode changes — the office is static geometry, so re-rendering ~140 casters every frame was waste. `RealisticCrowd` and `NameTags` each run **one** `useFrame` that drives every person through a registered-tick array instead of one R3F subscriber per person (~110 → 2), and `NameTags` returns `null` entirely unless employee mode is on or someone is selected.
- The Canvas is created with `antialias: true`. That flag is fixed at context creation so it cannot follow the quality tier — and postprocessing, which is where SMAA lives, is exactly what Fast and auto-tune's lower rungs give up first, so without MSAA those tiers render with *no* antialiasing at all onto a canvas that a large panel is already upscaling. When the composer does run it renders to its own target and the MSAA buffer costs only sample memory. `Scene.tsx` uses drei's `PerformanceMonitor` to step the canvas DPR between 0.8 and 2 from measured frame rate (`powerPreference: 'high-performance'`); `Effects.tsx` additionally drops postprocessing on sustained <28 FPS.

Loose reference images/screenshots at the repo root are design references, not app assets.
- `CustomOffice.tsx` is a dormant Sketchfab drop-in: it HEAD-probes `public/models/office/scene.gltf` (+3 variants) and, if the user has placed a model there, replaces the procedural `OfficeShell` auto-fitted to room dimensions. The directory does not exist by default.
- Room dimensions live in `DEFAULT_PARAMS.room` (`src/config/constants.ts`), default **30 × 20 × 3.6 m** (2,160 m³) — 3.6 m floor-to-slab so the suspended ceiling, LED bars and AC cassettes have headroom above standing people. Height is user-adjustable 2–12 m; every shell/ceiling/HVAC/pendant position is expressed as a fraction of `room.height`, so nothing needs touching when it changes. `NumberInput` takes a `step` (0.1 for height) and only rounds the display when the step is whole.
- The office layout is fully derived from room dimensions in `src/scene/office/officeLayout.ts`: desk pods (slid toward the room centre until their footprint clears every area), seats tagged `kind: 'desk' | 'meeting' | 'cafe'` (`facing(angle)` = (sin, cos); chairs sit 0.42 m and sitters 0.28 m behind the seat point — never assume angle is 0/π), standing spots, `areas` (glass `conference` hall on the back wall with an off-centre door, two glass `meeting` rooms in the back corners with doors toward the interior, open `cafeteria` front-right), `cafeTables`, `columns`, `planters`, and circle obstacles for the character controller. Obstacles are **circles or axis-aligned boxes** (`Obstacle`: `r`, or `hw`/`hd`). Round things — planters (r 0.42), columns, café tables, chairs (r 0.34, 0.42 m behind the seat point along the sitter's facing) — are circles. Desk pods, meeting/conference tables and lockers are **boxes**, because a circle around a rectangle is wrong in both directions at once: sized to cover the long axis it seals the aisle beside the short one, sized for the short axis it leaves the ends open. Pods sit on a 5.0 × 4.2 m pitch with 0.8 m aisles, so the pod box is `POD_HALF_W/D − 0.1` — the collider is inflated by the walker radius, and the full 2.1 × 1.7 half-extents would shrink those aisles to 0.2 m. Chairs and planters were meshes only, so you could walk through the seating and stand inside a meeting, or walk through a tree. `planters` is computed here rather than in `InteriorDecor` precisely because it is both decor and collider — positions derived in two places drift, and the symptom is furniture you can walk through. Per-zone seat order is one desk pod → meeting/café seats → remaining desks so moderate occupancy already shows meetings and breaks. `ConferenceRoom.tsx` renders every area (glass rooms + cafeteria rug/labels); `tableSize()` is the single source for meeting-table dimensions. Its glass is `meshPhysicalMaterial` with `ior` 1.52 + `envMapIntensity` — the realism comes from reflecting the HDR office rig, **never** from `transmission`, which forces an extra full scene render pass per pane. **Clearcoat is ultra-only**: it is a second full specular lobe on large, double-sided, transparent panes — the pixels a weak GPU can least afford to shade twice — and setting `clearcoat={0}` removes the `USE_CLEARCOAT` branch from the compiled shader rather than multiplying by zero. `envMapIntensity` goes 2.2 → 2.45 below ultra to carry the sheen it was adding, so the HDR character is unchanged; an A/B of the same view showed no visible difference. `HvacUnits.tsx` exports `ventPositions()` which the particle system imports for emitter placement. Its units are **instanced per part, not assembled per unit**: parts are laid out in world space up front so a cassette's body, vanes, grille and fan each become one draw for the whole office. Built the obvious way — a group per cassette — the ceiling units alone were 96 draw calls for ~1 k triangles, which is pure per-draw driver overhead. The fans and the AC louvers animate, but every fan shares one angle and every louver one sine, so `AnimatedInstanced` keeps them as a single instanced mesh whose matrices are rewritten once a frame. Do not turn these back into per-unit groups.
- **Where the frame time actually goes** (measured on the Intel UHD, fixed camera, auto-tune off, 1.29 MPix, 354 draws, 749 k triangles, 46 visible skinned meshes — hide one category and re-measure): baseline **47.8 fps**; hiding the airflow particles **47.8**; hiding the 26 transparent glass panes **47.8**; hiding *all* 45 transparent objects **48.1**; hiding the 46 skinned avatars **71.4**. Transparency, glass, overdraw and particles are free at this scale — **do not spend effort there**. The avatars are ~6.9 ms of a 20.9 ms frame, a third of it. And it is the *draws*, not the animation bookkeeping: an interleaved A/B/A that replaced `Skeleton.update()` with a no-op on all 268 skeletons (bone matrices and bone-texture uploads gone, geometry still drawn) measured 41.7/42.0/42.4 fps normal against 42.4/42.2 frozen — **no difference**. So the remaining in-app lever is avatar triangle count or avatar count, both of which stream GLBs and recompile shaders, which is exactly why they are off the auto-tune ladder. Note also that walkers moving in and out of frustum change the visible skinned count enough to swing a baseline from 71 to 43 fps within one run: **pin the camera and interleave A/B/A**, or the drift will read as an effect.
- **Airflow ribbons** (`src/scene/airflow/AirflowRibbons.tsx`): one glowing ribbon per zone, swept from that zone's ceiling vent down through a curl to breathing height near the zone centre — a continuous stroke of air, not a straight jet, because a four-way cassette does not blow straight down. Where the motes answer "is the plant running?", these answer "is the air reaching *me*?". Two channels carry it and they deliberately agree: **colour** lerps white → danger red on **outdoor air per person**, with the opacity ramp starting at zero on that same value so **clean air is invisible by construction** — a fine office draws nothing, the ribbon fades in only as the air degrades, and below a perceptible alpha the mesh's `visible` is cleared so the draw is skipped entirely, computed from the same `achFresh()` the engine integrates with and banded on the same 10 / 4 L/s thresholds `HvacCard` prints, so ribbon and card cannot tell different stories; and **motion** repeats it — the travelling streaks slow with ventilation and slow *further* as the zone goes red (measured 1.92 → 0.12, a 16× drop), so starved air visibly stops moving instead of merely changing hue. It reads `engine.snapshot`/`engine.params` inside `useFrame` and eases its own uniforms, like `AirflowParticles` — no React state. Cost is four draws and ~3 k triangles against a 354-draw, 749 k-triangle scene. When testing it, drive ventilation **through the store**, not `engine.setParams`: the ribbons read the engine and will update while the store-backed `HvacCard` stays stale, which looks like an inconsistency and is not one.
- **There are no ambient airflow particles.** `AirflowParticles.tsx` (motes from every vent, latterly motion streaks) was removed at the user's request. Worth knowing before anyone rebuilds it: as point sprites it read as floating dust; as vertical streaks it read unmistakably as **rain**, and the tell was **direction, not colour** — falling straight down from a ceiling vent is rain physics. Re-modelling the flow as a real cassette circulation loop (horizontal ceiling jet, sink at the walls, return along the floor) fixed the direction, and it was still cut. Recover it from git history rather than rewriting it. `AirflowRibbons` is now the only airflow visual.
- `Crowd.tsx` (largest file) renders up to `MAX_PEOPLE × 4` = 400 people via 14 parallel `InstancedMesh`es written from a single `useFrame` with shared scratch objects.
- **Navigation** (`src/scene/character/navigation.ts`): click-to-walk plans a route; it does not steer straight at the target. Collision alone is not navigation — pushing a walker out of what it entered leaves it pressed against the obstacle, and if the destination is straight beyond a desk run there is no sideways input to slide with, so it just stands there. Circles hid this (the push-out direction rotates, sliding you off by accident); an axis-aligned face does not, and the walker sticks. So the office is rasterised once into a 0.25 m walkability grid with obstacles inflated by the walker radius, A* finds a cell path, and a line-of-sight pass pulls it straight so the walker crosses a room on one diagonal rather than a grid staircase. Both ends snap to the nearest walkable cell — you can click a desk, and a seated avatar starts well inside its own pod. **Keyboard movement stays direct** (pathfinding your own WASD would feel like the controls fighting you). A seat is deliberately *inside* furniture, so the planner routes to the cell beside it and appends the seat as the final waypoint; the collider then exempts whatever *contains* that seat (containment, not a fixed radius — a 4 × 3.2 m pod needs it) plus the chair-sized circles within 1 m, since taking a free chair between two occupied ones means squeezing between them. Without that last exemption, adding chairs to the collider quietly made some free seats unreachable. A **stall watchdog** catches whatever still goes wrong: a live target with no movement for a beat replans once, then either sits (if within 1.5 m of a pending seat) or drops the target so control returns to the player — an avatar frozen against furniture believing it is still walking is the failure users actually notice.
- Character control (`useCharacterController.ts`): collision is resolved against obstacles inflated by `BODY_RADIUS` (0.3 m) over `COLLIDE_PASSES` passes, so the **body** stops against a table rather than its centre point reaching the table's edge, and standing in the corner between two obstacles settles instead of ping-ponging. The resolved position is fed back into `velocity`, so the walk animation and the heading follow where the body actually went and a walker pressed against a desk stops instead of grinding into it. Obstacles **stop** the walker, they never shove it. Approaching from outside, the step is clamped to the circle's rim, so walking into a table halts you against it and an oblique approach slides along it. Anyone *already* inside a circle — stood up out of a chair, or the layout changed under them — may move to any point no closer to the centre but never deeper; projecting them straight to the rim would teleport them out of the furniture, which reads as being thrown backwards rather than blocked. The `pendingSeat` exemption is what still lets F-to-sit walk through a chair's own obstacle to reach it. WASD **and the arrow keys are one scheme**: a camera-relative walk vector, with the heading always derived from the motion that actually happened, so **the body turns to face wherever it is going**. Arrows were previously a separate "controlled mode" relative to the avatar's own facing that *pinned* the heading — left/right side-stepped and down walked backwards without turning — which reads as a fault rather than a feature: press left and the avatar slides sideways still facing away, looking dragged rather than walked. Nothing pins the heading now. Verified by driving each key from an open aisle and comparing heading against the *instantaneous* direction of travel: worst mismatch 17 degrees, which is the body easing round while the path curves. Two cautions when testing this: compare against instantaneous velocity, never start-to-end displacement (the chase camera follows the heading, so a lateral key traces an arc and a curve's endpoints say nothing about its tangent), and discard any sample where speed is low — a walker pressed against a desk has residual push-out motion that reads as a 180-degree mismatch. Click-to-walk (`FloorClickTarget` in Scene.tsx) must also be preserved. A movement key in orbit mode auto-switches the camera to follow; ESC returns — handled on the **keydown event**, alongside F/G/J, never from the frame-polled key map, which `useKeyboard` clears on keyup so a tap that starts and ends inside one frame is never seen (at 20 fps on a large display that lost most taps and Esc looked broken). Follow cam is a spherical orbit around the player stored in `characterTransient` (`camDist`/`camYaw`/`camPitch`): **Q zooms in, Shift zooms out**, mouse drag on the canvas orbits (front/back/side views), wheel zooms — listeners are attached in `CameraRig.tsx`. There is no Q/E turning any more; **Ctrl + ← / → (or Ctrl + A / D) turns the body on the spot**, unbounded, so the avatar can be spun through a full circle without moving. Holding Ctrl zeroes the translation those same keys otherwise carry, so it pivots instead of strafing, and because `CameraRig` stores the chase yaw *relative to* `heading`, the view carries round with the body. **Space is jump** (`J` still works). Space is shared, so it yields: while a scripted presentation is running `PresentationOverlay` owns it for stepping scenes, and when a BUTTON/A/SELECT has focus the key is left alone so it still activates that control instead of launching the avatar — otherwise pressing Space right after clicking a navbar button both re-presses the button and jumps. It `preventDefault`s otherwise, or the page scrolls. Turning also counts as input that leaves the chair — without that Ctrl looks dead while seated, since a seat owns its sitter's facing. `useKeyboard` must `preventDefault` the Ctrl + A/D form: unprevented they reach Chrome as select-all and add-bookmark, and the bookmark dialog takes the page.

New artwork goes through `sharp` at ~1400 px wide, WebP q84, to stay in the ~25–170 kB band the others occupy.
  The right-wall hang is **width-aware**: widths are derived from each aspect, summed, and the leftover split into equal gaps, then laid out end to end and centred in the wall run. Do not go back to spacing frames at fixed fractions of the run — that ignores how wide each piece actually is, so a wide print crowds a narrow one and a large mural overlaps its neighbours outright. If the row will not fit, nothing is hung. `natpu` (the user-supplied portrait artwork; the id is the wall slot, not a description of whatever image currently fills it) is the centrepiece at 1.9 m tall, roughly twice its neighbours, and sits second in the row so it lands mid-wall; all frames share a 1.65 m hang line the way a real gallery hang does.

- **There is no loading screen.** It was removed at the user's request — they wanted the app to open rather than watch a progress bar. The shell paints and the office streams in behind it. What made that viable is that **`Scene` is `lazy()`-imported in `App.tsx`**: three.js + R3F + drei is ~1.5 MB, and importing it eagerly meant the browser parsed all of it before React could render *anything*, including the dashboard and live readouts, which need no WebGL. Measured cold on the production build, first paint went from **4.06 s to ~1.2 s** (1089/1152/1189/1273/1543 ms over five runs). Do not import `Scene` eagerly again. The startup cost that remains is **shader compilation — ~3 s, 26 % of all CPU samples in the first 11 s** and by far the largest single startup cost; it is spread across frames by `useAsyncCompile` rather than eliminated, so expect a handful of frames over 200 ms while the office builds. That storm was always there; the loading screen was hiding it.
- **Load-time rules** (`src/scene/useAsyncCompile.tsx`): three.js compiles a program on the first draw that uses it and the GPU process does that serially, so drawing the whole office at once froze the page for seconds. Every GLTF-backed subtree is wrapped in `<Compiled>` just inside its `<Suspense>` (and the whole initial `OfficeWorld` once): it mounts hidden and reveals two shader-variant groups per frame, compiling each just before it shows. `Compiled` also takes `deps`, and `OfficeWorld` passes the quality tier (and render mode) — a tier switch toggles the key light's shadow map, which changes the program cache key of **every** material (~34 programs), and re-streams the avatars' GLBs, and since the pacing only ran at mount all of those compiled on the first draw of one frame: measured as a single **4.2 s** frame on the Intel UHD for Fast → Balanced (5.4 s of synchronous `getProgramParameter`), 2.4 s back, 1.6 s for a Real/Styled toggle. With the tier in `deps` the office re-paces the same way it loads; the worst frame on those switches dropped to 0.75 s / 0.39 s / 0.23 s. Inside a Suspense boundary the effect fires at the commit that resolves the new content, which is when the new meshes exist. Keep new heavy subtrees inside a `Compiled`, and never let a `useGLTF` component render without a `Suspense` below the Canvas-level one (that single missing boundary on `RealisticBody` used to blank the entire scene until every model had loaded). `prepareAvatarSource()` strips leftover morph targets at runtime and `getRetargetedClips()` caches the Soldier→VALID retarget per model; `retargetMixamoClips` matches joints by name because the shipped Soldier has no skin. `gl.debug.checkShaderErrors` is off in production.

## Domain invariants (non-negotiable, from the spec)

1. **Never dramatize O₂.** `o2FromCo2()` derives it from CO₂ displacement (~20.7–20.95%); it is always badged SIMULATED (StatCard's `simulated` prop defaults to true).
2. **Not medical advice.** `effects.ts` / `HumanInsightPanel` / `PersonInspector` are illustrative population-level visualizations with permanent disclaimers; recommendations are environmental actions only.
3. **Occupancy alone ≠ danger** — CO₂ is generation vs. air-changes; the correlation view exists to make this point.
4. **Stale weather is labeled STALE**, never passed off as live.
5. **Occupants stay anonymous** (`Person A-03` IDs, no personal data).
6. Outdoor CO₂ is a constant 420 ppm (Open-Meteo has no CO₂ endpoint), tagged `E` (estimate).

Doc comments cite spec sections (e.g. `(spec §37)`) — continue that convention.

## Conventions

- TypeScript strict + `noUnusedLocals`/`noUnusedParameters`; `verbatimModuleSyntax` is on, so type-only imports must use `import type`.
- No path aliases — all imports are relative. Don't introduce `@/` without adding both tsconfig `paths` and Vite `resolve.alias`.
- Tailwind v4, CSS-first: the entire design system is the `@theme` block in `src/styles/index.css` (no tailwind.config.js). Theme tokens are used as utilities (`bg-panel`, `text-ink`, `text-ok`, `border-line`, …); `.glass` is the shared frosted panel, `.num` the monospace numeric style.
- `STATUS_COLORS`/`ACCENT_COLOR` in `src/config/constants.ts` intentionally duplicate the CSS theme vars so the palette works in both DOM and `THREE.Color` — keep them in sync.
- Determinism: use `seededRandom` from `src/utils/math.ts` for anything persistent across frames (crowd appearance, affected-person selection, textures) — never bare `Math.random()`.
